## PWA installation, cache and updates

The manifest uses `standalone`, repository-relative start/scope URLs and actual 192px/512px PNG icons. Its default identity follows the stable start URL: an explicit `id: "./"` would resolve against the origin and collide with a root deployment under the [manifest identity rules](https://www.w3.org/TR/appmanifest/#id-member). Keep the start URL stable once users install the app.

Visit the HTTPS Pages URL online first, then use the browser's install action when available. Installation is optional for the demo. The static shell is cached after a successful first visit; fictional drafts/images remain in IndexedDB on that origin. Localhost and Pages have separate storage, so local demonstration records do not transfer to the published URL. This is device-local persistence, with no server sync or backup.

Each deployment scope has its own versioned cache. Installation refreshes HTTP-cached asset URLs and records a scope/cache-bound SHA256 manifest of the complete snapshot. Reads use only the active cache; missing files are admitted only when their bytes match that installed manifest. Concurrent repair consumers own separate response bodies. Activation removes older caches for that same scope and retains other applications' caches. Legacy unscoped caches are retained because their ownership cannot be determined safely. Publish every runtime asset change with a new `VERSION` in `sw.js`; the current verified local version is **0.6.4**.

Settings shows the active worker version, update/download status, last successful check, verified offline-shell availability and browser/installed app mode. **Check for updates** is optional. The app checks automatically on startup, reconnection, return to the foreground (after 30 seconds), and hourly while visible. It bypasses the HTTP cache for worker checks with `updateViaCache: "none"`.

A downloaded version applies automatically when every open page in this deployment scope is ready. Dirty/busy editors and pending device-data operations defer it. Ready pages temporarily block interaction while the worker verifies readiness; a dirty, suspended, older or newly opened page cancels the attempt. Save completion or leaving the editor retries automatically, with a visible-page retry every 15 seconds. Controller change reloads each safe page once and preserves its hash route and IndexedDB records. Failed checks/downloads keep the active release and expose retry feedback. Offline status is separate from successful update checks and from server synchronization.

**Repair offline app** restores missing matching files and verifies the whole installed shell. If the server has different bytes or integrity metadata was lost, repair fails truthfully instead of mixing releases. **Install complete release** downloads a separate snapshot under a fresh worker identity and activates only after the same all-page readiness checks. Existing registrations retain their newest pending worker; reopening does not reverse a staged recovery. Neither action deletes IndexedDB records.

Cache diagnostics distinguish missing files, altered local cached files, unavailable integrity authority and an actually rejected server download. Local corruption offers matching repair; rejected server bytes can also be retried after the server restores the installed files. An incomplete waiting candidate does not change the active app's offline status or send repair to the wrong cache: use **Install complete release** to stage a fresh candidate. Page readiness, cache-check and activation failures have separate recovery instructions.

If a required module or HTML cannot load, the independent entry/recovery surface offers these controls and a native **Retry recovery online** link. Partial forms stay intact and block reload; save/copy their input or close that page before allowing the complete release to switch. Device counts stay unknown until records can actually be read. Normal safe updates retain the route; failed-boot recovery reopens the application root.

This automatic policy is an explicit project choice requested on 2026-10-13 and retained by the v0.6.0 remediation choice. It is a documented exception to the canonical KB `pwa:product-standard` v1.0 MUST requiring user-controlled activation, not a strict pass of that manual-update requirement. Dirty/busy protection and visible loading transitions remain mandatory. See the [service worker lifecycle](https://developer.chrome.com/docs/workbox/service-worker-lifecycle) and [updateViaCache contract](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/updateViaCache).

**Migration from version 29:** already open older pages retain their previous update logic. Save and reopen those pages once (or use their existing guarded Update now action) to load this policy. New automatic updates fail closed if an old/suspended page cannot confirm readiness; save and close that page to allow the next retry. No storage reset is required.

To recover a faulty release, revert its application changes in a new commit, increment `VERSION` in `sw.js` again, and deploy the corrected artifact. Real phone installation/camera, iOS standalone safe areas and browser-process cold launch still require device acceptance.

## PWA product standard remediation

Version 0.6.0 applies the canonical KB product standard within the existing local-demo scope. Shared `--safe-top/right/bottom/left` tokens use `env(..., 0px)` for the opaque top surface, navigation, content/notices, floating actions and update overlay. Editor clearance tracks its actual footer height; VisualViewport geometry adjusts footer position and focused-field visibility. Text/select/textarea controls use at least 16px, while mobile amount inputs retain 22px.

On long pages, the top bar hides after 48px of downward movement and reveals after 24px upward. Transforms preserve document geometry; routes, resizing, short pages, focused editing controls and expanded navigation keep it visible when needed. Return-to-top remains contextual, inset-aware and reduced-motion-aware. Settings load/reset/delete completion restores a usable focus target without stealing later focus or redrawing another editor.

[CODE_REVIEW.md](CODE_REVIEW.md#pwa-product-standard-audit-and-remediation) records the three new diagnostic/focus findings, UI gaps, passing-after evidence and exceptions. Dark-theme acceptance is not applicable to this light-only demo; actual iOS standalone/keyboard, OS installation and full screen-reader/contrast acceptance remain unverified. Snapshot checks and repair admission are not signed release authenticity or per-request verification of existing cache hits.

## Demo walkthrough

1. Open **Overview → Prepare a payable draft**, or **Projects → Cedar Station → New draft**. Cedar Station and Payable carry into the editor.
2. In **Details**, choose October 2026 and enter a fictional reference and period note. Save draft is available even while the record is incomplete.
3. In **Claim lines**, enter 10,000 for A01 and 15,000 for A02. The sample previous amount is 50,000; this period is 25,000 and cumulative is 75,000. Previous values are read-only synthetic fixtures. Harbor Exchange additionally includes the sample approved VO-007 line; Cedar Station has its own two-line basis. Quantity, rate, revised basis and source version are saved with new claim lines; old snapshots are preserved. No tax, retention or certification calculation occurs.
4. In **Evidence**, choose a sample text document and its claim/line context, then add it. Preview its actual fictional content. Ready to save becomes Saved on this device only after the draft transaction and read-back succeed. Evidence is optional in this demo.
5. In **Review**, inspect details, lines and sample evidence. The acknowledgement starts unchecked. **Save reviewed draft** records a local review and opens the detail page; it does not submit anything.
6. Use **Edit draft**, **Overview → Resume draft**, or **Device drafts** to continue. Saves keep the same identifier. Reload restores the last saved step and content. Older one-amount drafts resume as a preserved legacy line.

## Certification walkthrough

1. Save and locally review a valid fictional claim, then open its detail and choose **Start assessment**. The sample payable claim also provides an entry and a read-only example.
2. Enter each line's illustrative certified amount. The summary keeps claimed and certified separate; variance is certified minus claimed. Blank assessments remain unknown. Save draft accepts incomplete work; local review requires every amount and a reason for each non-zero variance.
3. Check the acknowledgement and choose **Save reviewed preview**. The resulting certificate detail is read-only and retains the exact saved source claim, line basis and supporting evidence. Later edits/deletion of the source do not rewrite it; the detail warns when the current source differs.
4. Resume incomplete assessments or open reviewed previews through **Claims → Open certificate previews** or **Device drafts**. Start a new assessment for another snapshot. Individual deletion and Settings clear affect only local certificate previews.

No certificate is issued. Retention, deductions, tax, net payable and PDF output await selected contract/output rules. Local previews do not change SOV figures, claims, invoices or payments.

## Evidence capture walkthrough

1. Save a fictional claim, then choose **Add evidence** on its detail or **Add image** in the saved editor's Evidence/Review step. A project Evidence page or **More → Evidence** also provides an entry. Save claim changes before leaving its editor to add an image.
2. Choose a fictional PNG/JPEG/WebP through the file picker, or choose **Load demo illustration**. The demo reads and decodes the actual file, checks type/signature, and limits it to 3 MB and 24 megapixels. An invalid selection retains the previous valid preview.
3. Check the project, saved claim and line (or Whole claim). Set the evidence type, user-supplied captured time, note and optional manual location. No device location is requested. The picker has a camera hint for supporting phones; real camera/device behavior is unverified.
4. **Ready to save** is a preview only. **Save on this device** persists image bytes and context together in a separate record, confirms the read-back, and opens its detail. Failed writes/read-backs keep the preview and details; retry the same attempt before leaving.
5. Browse project or global Evidence, search file/note/claim, and filter Photos/Documents. Existing synthetic text documents stay in their claim records; images have their own store. Device drafts provides image recovery links.
6. Saved claim Evidence/Review shows linked images as already saved, even when the claim has unsaved edits. A new certificate assessment copies the readable linked images for that project's claim into its source snapshot. Later image deletion does not alter a saved certificate.
7. Delete an image from its detail, or clear images through Settings. Confirmation is required. These actions keep claims, proposals and certificate snapshots; clearing claims also keeps the separately saved images and previews.

User-added images are device-local and unuploaded, with no server queue; bundled illustrations are read-only sample resources. Context snapshots remain available after a source changes or disappears; unreadable storage is shown as unavailable without hiding readable samples. Use fictional data only. Browser eviction or site-data clearing can remove device records.

## What works

- v2 shell: 240px desktop sidebar, expandable 72px tablet rail, five-item mobile browsing navigation and consistent outline icons. Focused mobile editing replaces bottom navigation with persistent Save/Continue actions and explicit back/close paths.
- Task-first Overview, synthetic projects and separate claimed/certified/invoiced/paid snapshot examples. Snapshot figures are independent fixtures, not aggregates of device drafts.
- Project Overview/SOV/Claims/Variations/Evidence navigation, responsive SOV/VO tables and cards, filters, source facts, truthful sample decision states, local proposal save/edit/review/delete and separate storage errors. Contract fixtures share one source; pending/rejected variations are excluded.
- Claim search, receivable/payable filters, short draft references and responsive list cards. Claim state and certification remain separate.
- IndexedDB draft create/edit/read/delete, incomplete draft saves, integer-cent illustrative line totals, local review and sample evidence content/metadata saved in one record. The existing claim store/key contract is unchanged. Variation proposals use a separate database and share only transaction handling.
- Validation and failure feedback retain input. Network changes preserve the editor, focus and selection. Leaving with unsaved changes requires an explicit discard decision; app updates wait for dirty/busy drafts to be saved.
- Mutable claim/proposal/assessment saves use transactional revision plus record-generation checks. Another tab's edits or deletion cannot be overwritten by an old snapshot; **Save as new draft/proposal/assessment** explicitly preserves conflicted input in a fresh unreviewed record. A same-ID practice reset also changes generation. These are device-local conflicts, not server synchronization.
- After a committed image/assessment write with failed confirmation, the exact receipt and save mode remain pending. Immutable attempt fields/mode are locked and the original Retry action confirms without duplicates; an aborted write still allows correction. A conflicting assessment can be explicitly saved as a separate unreviewed draft.
- Browsing refreshes on safe navigation/focus and committed cross-tab invalidation, preserving active editor input and browsing filters. Old-page delete/clear completion never redraws a later editor.
- Independent assessment drafts and read-only reviewed certificate previews, exact-cent signed variances, required reasons, source/evidence snapshots and guarded, idempotent retries. Certificates use a separate database; an atomic check prevents replacement of a reviewed preview by another tab.
- Image selection/preview, local bytes/context save/read-back, independent evidence gallery/detail, source context snapshots, note/location metadata, filters, failure/retry and separate delete/clear. Images are visible in claim review and copied into new certificate snapshots; existing claim storage is unchanged.
- A standalone manifest, deployment-scope cache isolation and safe automatic versioned updates. Hash routes resolve to the static shell. Chromium verified repository-subpath manifest parsing/installability diagnostics, guarded updates, cached reload/new-tab recovery and local writes after the artifact server was stopped.
- A GitHub Actions check-and-deploy workflow and validated runtime-only Pages artifact. Local artifact verification passes; a remote Actions run and live HTTPS smoke remain pending publication.

Browser storage can be evicted or cleared and is not a backup. Cache availability requires a successful first visit. Real device installation, browser-process cold launch, iOS standalone safe areas and screen-reader acceptance are not verified.

## Deliberately not implemented

There is **no authentication, authorization, tenant isolation, production API/database, server evidence upload, authoritative financial calculation, certificate issue, invoice/payment posting, audit ledger, AI, server synchronization or server conflict resolution**. Local image selection and guarded device-record conflict recovery are demonstrated; physical phone camera capture is unverified. Device records are not queued server commands. The demo cannot claim a server submission, approval, sync or financial event.

T-001–T-003 and production E2E-01–E2E-18 remain open. The wider 25-family design coverage is not a claim that all production routes exist.
